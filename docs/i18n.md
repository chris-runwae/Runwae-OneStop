# Localisation (i18n)

Runwae ships in 7 locales at launch. UI strings, date/number/currency formatting, and pluralisation are localised. Content (destinations, events, AI-generated trips, provider API data) stays in its source language and is a future enhancement.

## Supported locales

| Code | Language | Region | Notes |
|---|---|---|---|
| `en-GB` | English | UK | **Source of truth.** All translations derive from this file. |
| `en-US` | English | US | Generated by merging `en-GB.json` with `en-US.overrides.json` at module load (small set of spelling/word swaps). |
| `fr-FR` | French | France | LLM-generated; flagged as beta in app settings. |
| `es-MX` | Spanish | Mexico / LATAM | LLM-generated, beta. Uses `tú` informally; avoids Iberian-only vocabulary. |
| `es-ES` | Spanish | Spain | LLM-generated, beta. Uses Iberian conventions. |
| `pt-BR` | Portuguese | Brazil | LLM-generated, beta. Uses `você` throughout. |
| `it-IT` | Italian | Italy | LLM-generated, beta. |

All messages live in [`packages/i18n/messages/`](../packages/i18n/messages/).

## Adding or editing a string

1. **Edit `en-GB.json` only.** Never edit the generated locale files directly — they're overwritten on the next translation run.
2. Use a nested key path that reflects the surface: `auth.signIn.title`, `trip.members.errors.onlyOwner`, `payment.errors.cardDeclined`.
3. Use ICU MessageFormat for any string with interpolation or plurals:
   ```json
   "minutesAgo": "{count, plural, one {1 minute ago} other {# minutes ago}}",
   "greeting": "Hello, {name}"
   ```
   Placeholder names stay in English (`{name}`, `{email}`, `{count}`) — they don't get translated.
4. Run `pnpm --filter @runwae/i18n i18n:generate` to refresh all non-English locales.
5. For `en-US`, if your new string uses a UK-only spelling or idiom, add an override entry in `en-US.overrides.json`.

## Brand & glossary terms

These never get translated. Add to the `GLOSSARY_VERBATIM` list in [`packages/i18n/scripts/generate.ts`](../packages/i18n/scripts/generate.ts) when introducing new product nouns:

> Runwae, Discover, Stays, Fly, Do, Eat & Drink, Attend, Shop, Relax, Adventure, Explore, Apple, Google, Stripe

## Regenerating translations

```bash
# All non-English locales
pnpm --filter @runwae/i18n i18n:generate

# One locale only
pnpm --filter @runwae/i18n i18n:generate -- --locale=fr-FR

# Dry run (don't write files; useful for diff review)
pnpm --filter @runwae/i18n i18n:generate -- --dry-run
```

Requires `ANTHROPIC_API_KEY` in the environment. The generator uses `claude-haiku-4-5-20251001` and prompt caching, so a full 5-locale run typically costs well under $1.

The generator validates that each translated file has the same nested key structure as the source. If a key goes missing, the run fails for that locale.

## Locale resolution at runtime

1. If `users.locale` is set on the viewer's record, use it.
2. Otherwise read the device locale via `expo-localization` (mobile) or the `Accept-Language` header (web).
3. Resolve through `resolveLocale()` in [`packages/i18n/src/locales.ts`](../packages/i18n/src/locales.ts) — handles language-only inputs (e.g. `"fr"`, `"pt-PT"`) by mapping to the closest supported variant.
4. Fall back to `en-GB` if nothing matches.

The user can override this any time via **Profile → Appearance → Language**, which writes through `api.users.setLocale`.

## Adding a new locale post-launch

1. Add the BCP 47 tag to `SUPPORTED_LOCALES` in both:
   - `packages/i18n/src/locales.ts`
   - `packages/convex/convex/users.ts` (the inline `SUPPORTED_LOCALES` Set in `setLocale`)
2. Add a native-name label to `LOCALE_NATIVE_NAMES`.
3. Add an entry to `TARGET_LOCALES` in `packages/i18n/scripts/generate.ts` with locale-specific notes (formality, idioms).
4. Add the import + entry to `MESSAGES` in `packages/i18n/src/index.ts`.
5. Run the generator to produce the messages file.
6. Add the App Store localised metadata entry for the new locale.

## Upgrading to human-reviewed translations

The LLM-generated files at launch are marked as **beta** in the locale picker. The upgrade path:

1. Export `packages/i18n/messages/<locale>.json` into a translation management system (Lokalise, Crowdin, Tolgee).
2. Native-speaker reviewers edit auth, payment, and error strings first (highest-impact customer surfaces).
3. Import the reviewed file back into the repo, committing alongside a note removing the beta flag.
4. Update the locale picker copy: remove the "Translations are machine-generated" disclaimer for reviewed locales.

The disclaimer copy lives at `profile.appearance.language.betaNotice` in `en-GB.json`.

## Content (out of scope for v1)

These categories stay in their source language at launch:

- Admin-curated destinations and events (English-only authoring)
- AI-generated trip itineraries (Claude generates in the active locale, but the source schema doesn't store translations)
- Provider API data — Viator tour names, LiteAPI hotel descriptions, Ticketmaster events come through in whatever language the provider returns (typically English or the device-locale request hint)
- User-generated content — trip posts, polls, comments stay in the author's language

A future v1.1 effort will localise admin content at write time and request provider data per the active locale where supported.
